# Git Hooks

This project provides reusable Git hooks that execute the project's Docker-based development and security tools.

**Husky is optional.** The hooks can be used:

- directly with native Git hooks
- through Husky when a project already uses Husky

The actual hook implementation is always stored in `git-hooks/`.

## Architecture

```text
                    Git
                     │
             ┌───────┴────────┐
             │                │
        Native Git          Husky
          hooks               │
             │                │
             └───────┬────────┘
                     ▼
                git-hooks/
                     │
                     ▼
              Docker Compose
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
      Gitleaks     Trivy    Commitlint
```

Husky is only an optional integration layer. It is not required by the Git hooks themselves.

## Docker Compose Setup

The hooks run `docker compose` from the repository root. Docker Compose must therefore find a compose file at the root that includes the stack (when the stack is a submodule, see [Installing as a Git Submodule](#installing-as-a-git-submodule)):

```yaml
include:
  - docker-compose.stack.yml
```

`docker-compose.stack.yml` itself includes all the tool services (`docker/docker-compose.security.yml` and `docker/docker-compose.workflow.yml`).

### If the project already has a Docker Compose file

Add the `include` entry to the existing `compose.yaml` / `docker-compose.yml` at the repository root:

```yaml
include:
  - docker-compose.stack.yml

services:
  app:
    # existing services...
```

If the file already contains an `include` section, add `docker-compose.stack.yml` to the list.

### If the project has no Docker Compose file

Create a `compose.yaml` at the repository root:

```yaml
include:
  - docker-compose.stack.yml
```

### Check the setup

```sh
docker compose --profile security config --services
```

The output should list the stack services (`gitleaks`, `trivy`, `commitlint`, `sonarqube`, `cliff`, ...).

> [!IMPORTANT]
> Without this root compose file, every hook fails with `no configuration file provided: not found`.
>
> `include` requires Docker Compose v2.20 or later.

## Installing as a Git Submodule

The stack can be added to another project as a Git submodule, for example in `tools/docker-stack-process/`.

1. Add the submodule:

   ```sh
   git submodule add <stack-repository-url> tools/docker-stack-process
   ```

2. Include the stack in the project's root `compose.yaml`:

   ```yaml
   include:
     - tools/docker-stack-process/docker-compose.stack.yml
   ```

3. Install the hooks into the **parent** project (natively or with Husky):

   ```sh
   ./tools/docker-stack-process/install-hooks.sh
   # or
   ./tools/docker-stack-process/init-husky.sh
   ```

   The scripts detect the parent project automatically, and the hooks point to `tools/docker-stack-process/git-hooks/`.

4. For manual `docker compose` runs, add the line printed by the script to the parent project's `.env`:

   ```dotenv
   STACK_PROJECT_ROOT=../../../..
   ```

   `STACK_PROJECT_ROOT` is the project analyzed by the tools. It is resolved relative to `docker/<tool>/` inside the stack, so its value depends on where the submodule is installed (`../../../..` for `tools/docker-stack-process/`). The hooks set it automatically, so this step only matters for manual runs.

Other developers clone the project with its submodules:

```sh
git clone --recurse-submodules <project-url>
# or, in an existing clone
git submodule update --init
```

Then they run step 3 once.

> [!NOTE]
> If the submodule is not initialized, the hooks are skipped with a message. They do not block commits.

Update the stack to its latest version:

```sh
git submodule update --remote tools/docker-stack-process
git add tools/docker-stack-process
git commit -m "chore: update docker-stack-process"
```

## Using Git Hooks Without Husky

Husky is not required. Git hooks can be installed directly into `.git/hooks/`.

For example, the installed `.git/hooks/pre-commit` contains:

```sh
#!/bin/sh

# Installed by docker-stack-process (install-hooks.sh)

stack_hook="$(git rev-parse --show-toplevel)/./git-hooks/pre-commit"
if [ -f "$stack_hook" ]; then
    sh "$stack_hook" "$@"
else
    echo "docker-stack-process: $stack_hook not found, hook skipped (run: git submodule update --init)." >&2
fi
```

If the stack files are missing (for example, a submodule that is not initialized), the hook is skipped with a message instead of blocking the commit.

The hook source remains versioned in `git-hooks/pre-commit`, while `.git/hooks/` remains Git's local hook directory.

Because `.git/hooks/` is not versioned, each developer installs these wrappers with:

```sh
./install-hooks.sh
```

The wrappers call the versioned hooks, so changes in `git-hooks/` apply immediately without reinstalling.

> [!NOTE]
> If `core.hooksPath` is set (for example by Husky), Git ignores `.git/hooks/`. The script prints a warning in that case.

## Using Git Hooks With Husky

If the project uses Husky, the same hooks can be integrated into `.husky/`.

For example, `.husky/pre-commit` can contain:

```sh
#!/usr/bin/env sh

# docker-stack-process: pre-commit
stack_hook="$(git rev-parse --show-toplevel)/./git-hooks/pre-commit"
if [ -f "$stack_hook" ]; then
    sh "$stack_hook" "$@"
else
    echo "docker-stack-process: $stack_hook not found, hook skipped (run: git submodule update --init)." >&2
fi
```

Husky therefore acts only as the Git hook integration layer. The actual implementation remains `git-hooks/pre-commit`.

## Initializing Husky

The project provides `./init-husky.sh`.

The script:

1. Detects the target repository (the parent project when the stack is a submodule).
2. Checks whether `git-hooks/` exists.
3. Checks whether `.husky/` exists.
4. Detects available Git hooks.
5. Creates the corresponding Husky hook when necessary.
6. Adds the Docker hook execution to an existing Husky hook.
7. Avoids adding duplicate commands.

Run:

```sh
chmod +x init-husky.sh
./init-husky.sh
```

If the following exists:

```text
git-hooks/
├── pre-commit
└── commit-msg
```

the script registers these hooks in Husky.

### Existing Husky Hooks

Existing Husky hooks are **not overwritten**.

For example, if `.husky/pre-commit` already contains:

```sh
#!/usr/bin/env sh

pnpm run check-types
pnpm run test
```

the initialization script appends a block marked `# docker-stack-process: pre-commit`.

Result:

```sh
#!/usr/bin/env sh

pnpm run check-types
pnpm run test

# docker-stack-process: pre-commit
stack_hook="$(git rev-parse --show-toplevel)/./git-hooks/pre-commit"
if [ -f "$stack_hook" ]; then
    sh "$stack_hook" "$@"
else
    echo "docker-stack-process: $stack_hook not found, hook skipped (run: git submodule update --init)." >&2
fi
```

If the marker is already present, the block is not added again.

## Docker Git Hooks

The hooks can execute Docker Compose services directly.

### Pre-commit

```sh
#!/usr/bin/env sh

echo "================================"
echo " Running Gitleaks analysis"
echo "================================"

docker compose --profile security run --rm -T gitleaks
```

### Commit message

```sh
#!/usr/bin/env sh

docker compose --profile security run --rm -T --quiet-pull commitlint --edit "$1"
```

## Adding a New Hook

1. Create a new hook under `git-hooks/`:

   ```sh
   touch ./git-hooks/pre-push
   ```

2. Add the required logic:

   ```sh
   #!/usr/bin/env sh

   docker compose --profile security run --rm -T trivy
   ```

3. Make it executable:

   ```sh
   chmod +x ./git-hooks/pre-push
   ```

The hook can then be installed either:

- directly into `.git/hooks/` using `./install-hooks.sh`
- through Husky using `./init-husky.sh`

## Why Husky Is Optional

Keeping the actual hooks outside Husky provides a framework-independent setup.

A JavaScript project can use:

```text
Husky
  ↓
git-hooks/
  ↓
Docker
```

A Python, PHP, Go, Rust, or other project can use:

```text
Git
  ↓
git-hooks/
  ↓
Docker
```

The Docker tooling and hook implementation remain the same.

## Recommended Model

The recommended architecture is:

```text
                     git-hooks/
                         │
               ┌─────────┴─────────┐
               │                   │
        Native Git hooks         Husky
               │                   │
               └─────────┬─────────┘
                         ▼
                  Docker Compose
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Gitleaks         Trivy       Commitlint
```

This makes Husky an optional convenience layer, rather than a requirement of the project's Git tooling.
